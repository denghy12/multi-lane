# GPU0跨实验共享调度

用户于2026-10-23要求检查进度并利用空闲显存并行。检查时GPU0总24564MiB，仅使用3425MiB；模块叠加7/8组完成8任务，F111完成task2后进入task3；区域摘要与上下文Attention仍仅等待，无训练进度。叠加既有训练进程和控制器均保留。

新增独立调度分支exp/gpu0-shared-scheduling-20261023，仅增加外部控制脚本，不改三份科学源码工作树：叠加0fb85f1、区域摘要6bea373、上下文7c25e13。外部driver从各自干净工作树导入原批次函数，只替换子进程放行策略；训练入口、数据、seed、epoch、batch、优化器、学习率、任务顺序、监督及输出均沿用原方案。区域90% TRAIN/aux0.1与上下文全TRAIN/aux0.1仍是两个独立实验，不能混用基线。

安全移交：核验两个等待PID身份/工作目录、无子任务、正式与smoke输出未产生；保存旧队列状态和进程身份后，仅结束这两个等待控制器。原F111不暂停、不重启、checkpoint不覆盖。原队列标记移交，新控制器更新真实状态，不伪造前序实验完成标记。

GPU0采用共享fcntl锁，在子进程启动前原子预留每作业4500MiB，保留2000MiB余量，同时检查实际空闲至少6500MiB。叠加控制器仍活动时额外预留8000MiB，覆盖其将来4路评估；因此新增作业最多3个。叠加控制器结束后最多5个新增作业同时执行。各新子进程CUDA allocator上限16%，workers0、OMP1；区域局部最多3、上下文局部最多4，由全局预算进一步约束。启动前即预留可避免多个模型尚在CPU加载时都误判GPU空闲。

优先放行初始化与smoke，在同优先级内兼顾两组活跃数量。两个实验各自原GPU预检、恢复/重放审计全部保留，通过后才进入自身正式训练。模型间可以并行，一个模型内部8任务仍顺序学习。training/validation/test/归因仍受各自原依赖控制，任何失败不继续发新作业，保留现有产物。

这不是对所有并发度做穷举性能搜索；使用已知约2.6–2.8GiB训练峰值、实际空闲与预留余量，提高CPU图像读取和GPU计算的重叠。启动后核验真实并发、显存、跳步和完成状态，不能以显存占满替代吞吐评价。
