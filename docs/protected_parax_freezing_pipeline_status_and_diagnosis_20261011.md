# ParaX专家冻结与复用：八任务队列状态、故障定位和下一步

检查日期：2026-10-11。本报告只讨论本会话的专家冻结与复用，不合并其他会话的三路全量学习结果。

## 结论

**四组真实ViT八任务预检已结束；正式八任务、30 epoch/任务、三个seed的实验没有开始。**

预检训练进程均正常退出，最后的比较脚本因读取不存在的配置字段而报错。正式队列因此停止在启动门槛。当前不存在这批正式实验的validation/test结果，不能给出“八任务性能提升或下降”的结论。

我已同步319个远程日志、配置、分数和控制文件，逐文件SHA256核验一致（预检315个，正式队列4个）；未传输checkpoint。只在本地离线诊断中对应正确字段名后，完整比较审计全部通过。没有改服务器训练源码、门禁状态或checkpoint，也没有启动新训练。

## 二、失败发生在哪一步

流程为：四组预检训练与评估 → 比较与配对审计 → 生成预检完成标记 → 正式队列启动。

实际情况：

1. 四个worker都完成训练与评估，退出码都是0。
2. `multi_lane/track_a/protected_parax_compare.py`比较完整协议时，尝试读取`config['loss_routing']`。
3. `runner.py`实际保存的字段是`parameter_group_loss_routing`，四组值均为`joint_bce`。
4. 比较脚本抛出`KeyError: 'loss_routing'`，未写`completed.txt`。
5. 正式控制器发现预检控制器已退出但没有通过标记，保存`prerequisite_failed.json`，内容为`Smoke controller ended without passing comparison`。正式batch没有`started.txt`，也没有seed训练目录。

这不是显卡空闲不足、OOM、NaN或已观察到的模型遗忘导致的中断。根因是比较器与产物配置字段不一致；后续控制器又没有把比较阶段的具体异常写成结构化失败标记，因此正式队列只报告了较笼统的前置条件失败。

此前单元测试通过并没有覆盖“读取runner真实完整配置、执行八任务比较器”的集成路径，这是本次测试缺口。不能因为worker退出码为0就把整个流程说成成功。

源码：预检`eb04972`，正式队列`02abe58`。正式worktree仍为该commit且clean；两者没有本次分析造成的修改。

## 四、关于方法的有效结论仍来自之前三任务正式训练

下面是此前已完整训练的seed0、task0–2、validation结果，**不是本次八任务结果**：

| 实际方法 | 三任务最终mAP | 三任务平均mAP | 最终相对基线 |
|---|---:|---:|---:|
| 不加入ParaX的共享基线 | 44.3281 | 53.5698 | — |
| task0学专家池，后续冻结专家，只学当前任务Router和小投影 | 45.2055 | 54.8934 | +0.8773 |
| 每任务只学、使用自己的新专家 | 45.1656 | 54.8111 | +0.8374 |
| 冻结旧专家，组合旧专家并学习新专家 | 45.0411 | 54.8531 | +0.7130 |

这些结果的合理解释：

1. **保护旧路径与提升新任务是两件事。** 冻结旧专家、旧Router、小投影和访问集合，能够避免新任务改写旧任务实际使用的Adapter；之前固定旧人物的预测基本稳定。当前不应把所有问题继续归结为“共享中心必然漂移”。
2. **冻结小专家池有短程正面证据。** 最终+0.8773，但只有一个seed、三个任务，尚不清楚对后面任务是否仍然有用。
3. **增加并复用专家没有证明更好。** 复用组最终比只学新专家低0.1245，比冻结小池低0.1644；新增类收益在task1和task2方向不同。访问旧专家不等于成功利用旧知识。
4. **不能把收益全部归功于动态图像路由。** 同模型关闭残差后仍高于独立基线；开启残差额外约+0.26–0.27。原任务模块的训练轨迹、额外参数和动态残差的贡献必须区分。
5. **尚未证明三种level形成有效专门化，也没有动态融合。** 当前固定三视图融合始终保持不变。本会话暂不把这两个因素加入冻结实验。

复用不足的一个待验证机制是参数组合本身：先组合A矩阵、再组合B矩阵，其乘积含不同专家间的交叉项；即使旧专家被冻结，混合后也不自动等于“保留旧专家的完整功能”。这只是后续解释假设，当前没有实验单独证明它造成了下降，不能把它当作已定位原因。

## 五、下一步解决方案

### 先修实验流程，不改模型假设

1. 比较器严格读取真实的`parameter_group_loss_routing`字段；必须仍检查四组一致，不用`.get()`静默跳过缺失字段。若支持历史schema，应显式映射并检查冲突。
2. 从真实runner产物抽取最小八任务配置、指标和分数fixture，增加完整比较回归测试；同时覆盖字段缺失、四组loss配置不同、任务/测试分数缺失和更新预算不一致，确保失败仍会被发现。
3. 调度器单独记录比较阶段失败，例如`phase=comparison`、退出码、comparison.log路径及错误摘要；下游优先读取该具体失败原因。worker全部退出0不等于整个batch完成。
4. 在Git独立修复分支验证；保留原失败batch，不伪造`completed.txt`，不把预检checkpoint当正式续跑起点。
5. 若训练/审计实现完全未改，可先用修正版比较器重新审计现有预检产物，避免重复训练；只有修改模型、训练或identity审计逻辑才重跑相应预检。之后以新的控制记录和batch启动正式实验，记录训练源码与审核器各自commit，避免来源歧义。

### 再执行原定正式四组，不叠加新变量

原定四组×seed0/1/2、task0–7、30 epoch/任务；从预训练CLIP和配对随机初始化重新开始。保持Task Forward输出后的ParaX位置、rank32、两个新专家/任务、2%可微残差界、固定融合等配置。每次训练的相同权重同时评估validation/test，不按test选择checkpoint或调参；预检test不参与方法选择。

本轮不加Projector、蒸馏、level embedding、动态融合或新的分阶段训练。先回答冻结小池能否持续有效，以及旧专家复用是否比相同新增预算更好。

### 正式结果到齐后的判断

- 冻结池在三个seed大多数配对差值为正，后期新类不系统性变差，固定旧样本稳定：保留小冻结池继续机制分析。
- 冻结池前期有效、后期新类下降，但固定旧样本稳定：问题主要是旧池对新类的适配能力不足，不能解释成旧中心被更新。再考虑是否需要少量新增专家。
- 复用旧专家不优于只学新专家：不能声称跨任务知识复用；优先保留更简单、参数增长更小的方法。必要时后续单独测试“旧/新池分别组合、池间受控混合”并控制容量预算。
- 旧样本在充分训练后明显漂移：先检查旧Router、投影、访问mask、归一化和上游共享参数是否也封存，再考虑额外稳定机制。
- 正式收益接近seed波动或反向：先停止扩大专家池，以匹配参数预算的静态路由对照查明短程收益来源。
